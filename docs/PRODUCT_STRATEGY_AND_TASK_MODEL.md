> 来源：围绕「功能与实现评价 → 商业价值 → 竞品借鉴 → 工程师刚需 → 碎片化任务处理」的连续讨论汇总

## 0. 结论摘要

1. **产品力领先、商业化缺位**：工程实现处于同类单人项目的上游（4.3 万行前端 / 6.4 千行 Rust / 762 单测），但代码中不存在任何 License 校验、试用、支付或埋点，当前收入路径为零。
2. **价值链位置太浅**：现有能力止步于「读懂标准」，而钱在「判定」与「交付」。竞品（Hardware Compliance / StanDocs）的终点都是可交付文档，不是回答。
3. **真正的刚需只有两条主线**：判断「这条管不管我这个产品」（适用性）与「数据对不对得上限值」（判定）。其余环节都是围绕它们的记录工作。
4. **碎片化任务不靠"更小的 agent"，靠"可以沉淀的卡片"**：以「探究卡」为最小判断单元，任务不是前置条件，而是卡片攒够后的聚合结果。
5. **下一步三件事**：表格结构化取数（限值库）→ 判定表（数据 vs 限值）→ 清单/报告导出（可签核）。这三件串起来才构成按席位收费的理由。

## 2. 市场与竞品

### 2.1 Hardware Compliance

面向硬件厂商的产品认证全流程，销售主导（对标咨询费 2–10 万美元、3–6 个月）。

链路：上传产品规格与目标市场 → AI 判定适用标准 → 逐条给需求并附带**精确页码/条款引用** → 生成技术文件、危害分析、EMC/安全测试计划、DoC → 匹配实验室 → 专家复核背书。看板呈现「适用标准数 / 已生成文档 / 完成度 / 实验室匹配度」。

值得注意的三点：**以文档为交付终点**、**引用必须精确到页与条款**、**人工复核是溢价来源**。

### 2.2 StanDocs

面向工程团队的内部标准 AI workforce，SaaS 按席位收费：Essential $99、Professional $149 每人每月，年付 $825 / $1,232，1 个月试用；Enterprise 提供 SSO、审计日志、私有 Agent、发票结算。

核心结构：75+ 任务化 Agent（合规/需求/测试/文档/安全/质量/设计/EMC/环境/追溯/审核/风险 12 类）+ Agent 推荐引擎 + 项目工作区协作 + **把外部标准合成为公司版标准** + 差距分析与合规评分 + 追溯矩阵 + Agent Manager 治理 + MCP + 自带 Key。

两个可直接引用的结论：**即使客户自带 API Key，软件仍可按席位卖 $99–149/月**（软件价值与 token 成本解耦）；**任务化 Agent 比万能聊天框更接近真实工作方式**。

### 2.3 其他威胁面

- **WPS 365**：已内置「AI 标准解读助手」（条款知识图谱、checklist 生成、版本变更追踪），随办公套件打包，是价格与分发的双重压制。
- **ChatPDF / Adobe / NotebookLM**：吃掉通用「与文档对话」需求，且默认上传云端，与本产品信任模型错位。
- **传统咨询与实验室**：仍是客户现状基线，也是定价锚。

### 2.5 明确不照搬

- **实验室匹配**：不同生意，最多外链。
- **云端上传标准**：与本地优先、客户保密正面冲突，是唯一信任资产。

- **纯销售主导**：对方是 enterprise sales-led，本产品应走 PLG + 团队版。

## 3. 刚需定义

### 3.1 三条判据

同时满足才算刚需：① 每单必做（频次）；② 做错要返工/召回/丢资质（代价）；③ 通用工具替代不了（壁垒）。只中一条的是爽点。

### 3.2 六项真刚需

| #   | 刚需                                   | 为什么不可替代                               | 做对的验收标准                                                  | 现状                 |
| --- | -------------------------------------- | -------------------------------------------- | --------------------------------------------------------------- | -------------------- |
| 1   | 条款适用性判定（Scope/分类/豁免/条件） | 错判即漏测，证书带病；无工具可替代           | 输出适用/不适用/条件适用 + 依据条款 + 原文 + 理由，可直接进报告 | 空白                 |
| 2   | 限值表与表格精确取数                   | 判定的唯一依据，读错一行即事故               | 值 + 表号 + 行标识 + 页面图证，可核对                           | 有截图通道，未结构化 |
| 3   | 判定辅助（数据 → PASS/FAIL）           | 报告结论的生成器，含环境修正/材料分类/单故障 | 逐项结论 + 引用限值 + 边界条件说明                              | 空白                 |
| 4   | 测试项目清单/结构检查表                | 系列型号复用的核心资产                       | 可勾选、可克隆改差异、可导出、可签核                            | 空白                 |
| 5   | 引用链追踪（Clause/Annex/跨标准）      | 跨标准引用人脑撑不住，漏引即 NC              | 链路面包屑 + 目标原文 + 一键跳转                                | 单跳悬停预览         |
| 6   | 版本差异与换版影响                     | 换版一旦发生即全项目级需求                   | 条款级 diff + 对既有报告/证书的影响判定                         | 有分屏，无 diff      |

### 3.3 三类伪刚需

| 伪刚需          | 判断                                                            |
| --------------- | --------------------------------------------------------------- |
| 通用翻译 / 摘要 | 高频但不进交付物，DeepL/沉浸式翻译/WPS 可替代，不构成换工具理由 |
| 全文问答聊天    | 问答不产生记录，报告里不能写「AI 说」；是入口体验，不是价值终点 |
| 花哨阅读体验    | 决定留存，不决定付费；不可砍，但不可当卖点                      |

### 3.4 四类角色的差异

| 角色             | 关心什么                         | 对应刚需     |
| ---------------- | -------------------------------- | ------------ |
| 测试工程师       | 限值、判定、工装与仪器           | 2、3         |
| 项目工程师（PE） | 适用性、计划、客户沟通、报告主体 | 1、4、5      |
| 认证决定 / 审核  | 引用完整性、偏离评估、签核       | 5、7（签核） |
| 工厂检查         | 一致性、CDF、标识                | 4            |

付费决策人通常是实验室经理，其诉求是「报告少返工、审核少开 NC」，对应 3、4、5。产品体验面服务 PE 与测试工程师，价值主张要打到管理者。

## 4. 任务-卡片模型（核心提案）

### 4.1 问题陈述

工程师的工作不是一条完整的认证流水线，而是大量碎片：判定一个条款是否适用、解读一个测试流程、梳理一个条款里的细节。大而规范的任务可以建专门 agent 跟踪，小任务小问题如果只落到聊天记录里就会蒸发——既不能复用，也不能交付，还挤占注意力。

结论：**碎片不需要更小的 agent，需要更低的启动成本 + 不蒸发的沉淀物。**

### 4.2 对象模型

| 对象               | 定义                                                                  | 生命周期    | 存储                             |
| ------------------ | --------------------------------------------------------------------- | ----------- | -------------------------------- |
| **Task（任务）**   | 一个项目/报告追踪体：清单、进度、上下文（产品画像、目标市场、标准集） | 周 ~ 月     | `AppData/tasks/{id}.json`        |
| **Card（探究卡）** | 一次判断的最小单元：类型、结论、依据、置信度、状态                    | 分钟 ~ 永久 | `annotations/{hash}/cards.jsonl` |

两者不是父子，而是**可挂载**：卡片可独立存在、可丢弃、可挂到任务清单项；任务清单项也能反向生出卡片。**任务不是前置条件，而是碎片的聚合结果**——桌面工具最忌讳「先建项目再干活」。

### 4.3 流转：一个入口，三个出口

```
选中条款 ─┐
无选区提问 ─┼→ 探究卡（type + 结论 + 依据 + 状态） ─┬→ 丢弃（不留痕）
清单项追问 ─┘                                      ├→ 案头收件箱（按文档聚合）
                                                   └→ 挂到任务清单项
```

- **入口只有一个**：`SelectionToolbar` 增加「判定」，无选区直接问。
- **出口必须明确**：丢弃 / 进案头 / 挂任务。最怕第四种「沉在聊天记录」。
- **快问与判定用同一个动作区分**：快问 = Enter，答完即走、不写盘；判定 = 点按钮，产出结构化卡片。区别在意图，不在多一步操作。

### 4.4 六种作业形态

不是六个 agent，而是 prompt + 工具白名单 + 输出 schema + 卡片渲染器的组合。**形态统一，内容按类型变化**。

| 形态       | 触发            | 输出                                   | 沉淀为               |
| ---------- | --------------- | -------------------------------------- | -------------------- |
| 适用性判定 | 选中 Scope/条款 | 适用 / 不适用 / 条件适用 + 依据 + 理由 | 判定卡，可导出判断表 |
| 流程解读   | 选中测试条款    | 步骤序列 + 每步判据 + 仪器/样品/前置   | 步骤表 / 流程图      |
| 细节梳理   | 选中整节        | **多张卡**：条件 / 限值 / 例外 / 引用  | 卡片集               |
| 取数       | 选中表格        | 单元格值 + 表号 + 行标识 + 图证        | 限值条目             |
| 比对       | 两版 / 两文档   | 差异清单 + 影响判定                    | 差异卡               |
| 追溯       | 选中引用        | 引用链面包屑 + 目标原文                | 追溯链               |

「细节梳理」必须支持**批量**：按条款区间扫一遍生成卡片集，在案头逐条确认——这才符合「梳理」的真实动作。

### 4.5 上下文装配规则

碎片最大的风险是脱离上下文却答得头头是道。每张卡固定装配：

1. 本条款原文；
2. 本章 Scope 与定义；
3. 自动检索的 3 条相关引用；
4. 产品画像（若有）；
5. 客户特殊要求（若有）。

卡片上必须明示「我依据了这 5 处，点开可核对」。缺 Scope 时禁止装懂，标注「未找到适用范围章节，结论仅供参考」。任务内的卡片额外注入任务上下文（产品/市场/标准集/清单进度），让用户不必复述。

### 4.6 数据结构

```ts
type InquiryCard = {
  id: string;
  fileHash: string;
  page: number;
  clause?: string;
  kind: "applicability" | "procedure" | "detail" | "value" | "diff" | "trace";
  question: string;
  answer: string; // markdown
  citations: { page: number; clause?: string; quote: string }[];
  verdict?: {
    value: "applicable" | "not" | "conditional";
    confidence: number;
    basis: string[];
  };
  status: "draft" | "confirmed" | "rejected";
  taskId?: string;
  taskItemId?: string;
  createdAt: number;
};
```

存储约定：`cards.jsonl` 追加写，一卡一行；卡片轻（KB 级），不与会话混存；会话仍然只承担多轮深挖。

### 4.7 任务从碎片里长出来（bottom-up）

不做「先建任务」，做事后聚合：

1. 案头收件箱按文档/产品线聚合卡片；
2. 同一标准攒到 8–10 张时提示「可合并为一个任务」；
3. 一键生成骨架：已覆盖的进清单，**未覆盖的条款留空标记**；
4. 任务清单项点开 → 生成卡片 → 确认后回写该项状态。

用户从「我在读标准」滑到「我在管项目」，全程不填表单。任务因此是「活」的，而不是又一个手填表格。

### 4.8 状态机

`draft`（AI 产出）→ `confirmed`（工程师确认）→ 可导出/可挂任务；`draft` → `rejected`（驳回，保留理由供复盘）。**未附引用的卡片禁止进入 confirmed**，这是可审计性的底线。

### 4.9 失败模式与对策

| 失败模式         | 对策                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| 卡片泛滥         | 同（hash + 条款 + kind）命中即提示复用不重跑（顺带省钱）；7 天未确认自动归档；同页超 5 张折叠成组 |
| 上下文缺失误判   | 依据必须可见；无引用不得 confirmed；缺 Scope 显式降级提示                                         |
| 聚合半途而废     | 合并先给骨架与缺口清单，不让用户面对空白任务                                                      |
| 重复提问烧 token | 指纹 =（hash, 条款, kind, 问题归一化），命中复用并标注「1 小时前已判定」                          |

## 8. 风险与对策

| 风险                             | 影响             | 对策                                                                                 |
| -------------------------------- | ---------------- | ------------------------------------------------------------------------------------ |
| WPS 365 内置标准解读并捆绑分发   | 中高端客户被截流 | 不拼通用解读，拼「客户要求 + 内部 SOP 的公司版」与可签核交付物                       |

| 团队版需要服务端，与本地优先冲突 | 中               | 私有化部署优先，服务端只承载授权/模板/共享库，不承载文档                             |

## 9. 待决问题

1. **卡片的归属粒度**：按 `fileHash` 还是按「项目」？跨版本（同一标准两版）如何归并？
